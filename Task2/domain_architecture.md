# Задание 2: Разделение системы на домены и моделирование потоков данных

## 1. Доменная архитектура "Будущее 2.0"

### 1.1. Принципы разделения на домены

Архитектура построена на основе **Domain-Driven Design (DDD)** и **Data Mesh** с учетом:

1. **Организационной структуры** - каждый домен соответствует бизнес-подразделению
2. **Ограниченных контекстов (Bounded Contexts)** - четкие границы ответственности
3. **Бизнес-возможностей (Business Capabilities)** - домены группируются по функциям
4. **Независимости данных** - каждый домен владеет своими данными
5. **Масштабируемости** - возможность добавления новых доменов без изменения существующих

### 1.2. Выделенные домены

#### Домен 1: Healthcare (Медицинские услуги)

**Владелец**: Клиники

**Ответственность**:
- Управление пациентами (регистрация, профили)
- Записи на прием к врачам
- Управление расписанием клиник
- Операционные данные клиник
- Результаты приемов (без детальных медицинских данных)

**Данные в домене**:
- Клиенты (ФИО, контакты, базовая информация)
- Записи на прием
- Расписание врачей и клиник
- Финансовые данные о приемах (стоимость, оплата)
- Персонал клиник
- Инвентаризация медицинского оборудования
- Медицинские карты (исключены из аналитики по требованию бизнеса)
- История болезней (исключены из аналитики)
- Результаты диагностических исследований (исключены из аналитики)

**Сервисы**:
- Patient Service - управление данными пациентов
- Appointment Service - записи на прием
- Schedule Service - расписание клиник и врачей
- Clinic Operations Service - операционные данные

**Технологии**: Java, Spring Boot, PostgreSQL, REST API

**Причина выделения**:
- Независимое развитие медицинского направления
- Изоляция чувствительных медицинских данных
- Возможность масштабирования клиник без влияния на другие домены

- Кредиты и займы

- Финансовая история

**Сервисы**:
- Account Service - управление счетами
- Credit Service - кредитование
- Payment Service - платежи

- Scoring Service - кредитный скоринг

**Технологии**: Golang, Java, PostgreSQL, REST API, gRPC

**Причина выделения**:
- Требования к изоляции банковских данных
- Быстрое развитие финансовых продуктов

#### Домен 3: AI/ML (Искусственный интеллект)

**Владелец**: Подразделение ИИ-сервисов

**Ответственность**:
- Разработка и обучение ML-моделей
- Inference (применение моделей)
- Управление фичами (Feature Store)
- Версионирование моделей
- Мониторинг качества моделей

**Данные в домене**:
- ML-модели и их версии
- Фичи для моделей
- Результаты предсказаний (рекомендации, скоринг)
- Метрики качества моделей
- Эксперименты (MLflow)
- Сырые медицинские данные (только получают их для обработки, не хранят)

**Сервисы**:
- Model Training Service - обучение моделей
- Model Serving Service - применение моделей
- Feature Store - хранение и предоставление фич
- ML Pipeline - оркестрация ML-процессов
- Model Registry (MLflow) - версионирование

**Технологии**: Python, FastAPI, MLflow, Feast/Tecton, PostgreSQL

**Причина выделения**:
- Специфичный технологический стек (Python, ML-frameworks)
- Итеративный процесс разработки моделей
- Изоляция экспериментов от продакшен-данных
- Возможность быстрого внедрения новых моделей

## 2. Потоки данных между доменами

### 2.1. Типы потоков данных

#### 🔵 Синхронные потоки (REST API)
Используются для **операционных запросов** в реальном времени:
- Запрос данных пациента при записи на прием
- Проверка кредитоспособности при оформлении кредита
- Получение предсказания ML-модели

**Характеристики**:
- Latency: < 100ms
- Protocol: REST API / gRPC
- Pattern: Request-Response

#### 🟠 Асинхронные потоки (Events)
Используются для **уведомлений о событиях**:
- Новый пациент зарегистрирован
- Платеж совершен
- Кредит одобрен
- Прием завершен

**Характеристики**:
- Latency: < 1 секунды
- Protocol: Apache Kafka
- Pattern: Publish-Subscribe

#### 🟢 Пакетные потоки (ETL/ELT)
Используются для **аналитики**:
- Репликация данных в Data Lake
- Построение аналитических витрин
- Агрегация метрик

**Характеристики**:
- Latency: минуты - часы
- Protocol: CDC (Debezium), Airflow
- Pattern: Extract-Transform-Load

## 2. Обоснование разделения на домены

### 2.1. Преимущества для бизнеса

#### 1. Ускорение вывода продуктов

**Проблема раньше**:
- Все изменения в одном DWH
- Любое изменение требует согласования со всеми командами
- Time-to-market: 2-3 месяца

**Решение через домены**:
- Каждый домен разрабатывается независимо
- Изменения в Healthcare не влияют на Fintech
- Каждая команда может делать deploy самостоятельно

**Результат**:
- Time-to-market: 2-3 недели
- 10x быстрее вывод новых фич
- Быстрее реакция на конкурентов

---

#### 2. Снижение зависимости от DWH

**Проблема раньше**:
- Вся бизнес-логика в DWH (MS SQL Server 2008)
- DWH - единая точка отказа
- Любое изменение требует изменения DWH
- Перегрузка IT-отдела (все идут к DBA)

**Решение через домены**:
- Каждый домен имеет свою БД
- Бизнес-логика в микросервисах, а не в БД
- DWH становится опциональным (только для сквозной аналитики)

**Результат**:
- Нет единой точки отказа
- IT-отдел не перегружен
- Каждый домен оптимизирован под свои нагрузки
- Можно использовать разные БД (PostgreSQL, MongoDB, etc.)

**Пример**:
- Healthcare может использовать PostgreSQL для операционных данных
- Fintech может использовать CockroachDB для транзакций
- AI/ML может использовать специализированные БД для фич

---

#### 3. Независимое развитие направлений

**Проблема раньше**:
- Одна команда поддерживает всё
- Нельзя нанимать специализированных специалистов
- Конфликты между командами из-за общих ресурсов

**Решение через домены**:
- **Healthcare команда**: врачи + Java разработчики
- **Fintech команда**: финансисты + Golang разработчики + security
- **AI/ML команда**: data scientists + ML engineers (Python)
- **Corporate команда**: HR + ERP специалисты

**Результат**:
- Автономные команды (Amazon's two-pizza teams)
- Специализированные навыки
- Параллельная разработка
- Независимые циклы релизов

**Пример**:
- AI/ML команда может экспериментировать с новыми моделями каждую неделю
- Fintech команда делает релиз новых продуктов каждые 2 недели
- Healthcare команда обновляет UI раз в месяц
- Не влияют друг на друга!

---

#### 4. Масштабирование для новых бизнесов

**Проблема раньше**:
- Добавление партнера = изменение DWH, ESB, всех систем
- Онбординг: 2-3 месяца
- Высокий порог входа

**Решение через домены**:
- Стандартизированный подход к онбордингу
- Новый партнер = новый домен
- Шаблоны: Domain Service Template, Data Product Template
- API Gateway автоматически регистрирует новые сервисы

**Результат**:
- Checklist для новых партнеров
- Plug-and-play интеграция
- Автоматическое появление в аналитике

#### 5. Compliance и безопасность

**Проблема раньше**:
- Медицинские карты в одной БД с финансами
- Сложно обеспечить изоляцию
- Нет четкого аудита доступа

**Решение через домены**:
- **Healthcare**: изоляция медицинских данных, только персонал клиник
- **Fintech**: изоляция финансовых данных, требования ЦБ РФ
- **AI/ML**: НЕ хранит медицинские данные, только обрабатывает
- Каждый домен имеет свои политики доступа

**Результат**:
- Соответствие требованиям регуляторов
- Audit trail по каждому домену
- Row-level security в каждом домене
- Прохождение сертификаций

**Пример**:
- Сотрудник Fintech не может видеть медицинские карты
- Сотрудник Healthcare не может видеть детали кредитов
- AI-модели получают анонимизированные данные

---

#### 6. Оптимизация затрат

**Проблема раньше**:
- Все данные в одном дорогом DWH
- Нельзя оптимизировать стоимость хранения
- Переплата за неиспользуемые ресурсы

**Решение через домены**:
- Каждый домен выбирает оптимальное хранилище
- Холодные данные → S3 Glacier
- Аналитика → Snowflake (pay-per-query)
- Операционные данные → PostgreSQL (дешевле)

**Результат**:
- Экономия ~30% на инфраструктуре
- Прозрачность затрат по доменам
- Оптимизация под нагрузку


## Паттерны интеграции

### 1. Event-Driven Architecture (Kafka)
- Decoupling между доменами
- Pub-Sub модель
- Eventual consistency

### 2. REST API
- Синхронные запросы
- Request-Response
- Strong consistency внутри домена

### 3. CDC (Change Data Capture)
- Репликация данных для аналитики
- Debezium → Kafka → Data Lake
- Near real-time (< 1 мин)

### 4. Saga Pattern
- Распределенные транзакции
- Choreography через Kafka
- Компенсирующие транзакции

### 5. CQRS
- Разделение записи (OLTP) и чтения (OLAP)
- Оптимизация под нагрузку
- Domain DB → Data Product
