# Задание 1: Целевая архитектура и приоритизация проблем

## 1. Целевая архитектура "Будущее 2.0" (через год)

### 1.1. Архитектурный подход

Целевая архитектура основана на принципах **Data Mesh** и **Domain-Driven Design**:

- **Децентрализация данных**: каждый домен владеет своими данными и бизнес-логикой
- **Data Products**: домены предоставляют данные как продукты через стандартизированные интерфейсы
- **Self-Service Platform**: единая платформа для доступа к данным и построения отчетов
- **Federated Governance**: централизованное управление политиками при автономии доменов
- **Облачная инфраструктура**: гибкое масштабирование и отказоустойчивость

### 1.2. Доменная структура

#### 1.2.1. Медицинский домен (Healthcare Domain)
- **Владелец**: Клиники
- **Данные**: клиенты, записи на прием, операционные данные клиник
- **Исключены из аналитики**: медицинские карты, истории болезней, результаты исследований
- **Технологии**: операционные БД (PostgreSQL), Domain Data Product (аналитическая витрина)

#### 1.2.2. Финтех домен (Fintech Domain)
- **Владелец**: Банковское подразделение
- **Данные**: счета, кредиты, транзакции, финансовая история клиентов
- **Технологии**: микросервисы на Golang/Java, PostgreSQL, Domain Data Product

#### 1.2.3. ИИ домен (AI/ML Domain)
- **Владелец**: Подразделение ИИ-сервисов
- **Данные**: результаты анализа (не сами медицинские данные), модели, метрики моделей
- **Технологии**: Python, MLflow, Feature Store, Domain Data Product

#### 1.2.4. Корпоративный домен (Corporate Domain)
- **Владелец**: Головной офис
- **Данные**: персонал, инвентаризация, финансовая отчетность, управление
- **Технологии**: ERP-система, PostgreSQL, Domain Data Product

### 1.3. Ключевые компоненты архитектуры

#### Слой источников данных (Source Layer)
- **Медицинская операционная система**: PostgreSQL кластер для клиник
- **Финтех-сервисы**: микросервисы с собственными БД
- **ИИ-сервисы**: Python-приложения с Feature Store
- **Корпоративные системы**: ERP, HR, WMS

#### Слой интеграции (Integration Layer)
- **Event Streaming**: Apache Kafka для потоковой передачи событий
- **API Gateway**: Kong/AWS API Gateway для REST API
- **CDC (Change Data Capture)**: Debezium для захвата изменений из БД
- **Batch ETL**: Airflow для пакетной загрузки

#### Слой хранения данных (Data Storage Layer)
- **Data Lake**: S3/Azure Data Lake для хранения сырых данных
  - Raw Zone: исходные данные в оригинальном формате
  - Curated Zone: очищенные и структурированные данные
- **Domain Data Products**: выделенные хранилища данных по доменам
  - Snowflake/BigQuery/Azure Synapse для аналитических запросов
  - Оптимизированные модели данных (star schema)
- **Data Catalog**: Unity Catalog/AWS Glue для метаданных и governance

#### Слой аналитики и доступа (Analytics & Access Layer)
- **Self-Service Portal**: веб-приложение для самообслуживания
  - Конструктор отчетов
  - Готовые дашборды
  - Управление доступом (RBAC)
  - Интеграция с Data Catalog
- **BI Platform**: Power BI (модернизированный) / Tableau
- **Data Warehouse**: централизованное хранилище для сквозной аналитики
  - Только агрегированные метрики из доменов
  - Не содержит детальные операционные данные

#### Слой управления и безопасности (Governance & Security Layer)
- **Identity & Access Management**: Azure AD/AWS IAM
- **Data Governance**: политики доступа, классификация данных
- **Audit & Compliance**: логирование доступа к медицинским и финансовым данным
- **Data Quality**: Great Expectations/Soda для контроля качества

### 1.4. Технологический стек целевой архитектуры

| Компонент | Текущее состояние | Целевое состояние |
|-----------|-------------------|-------------------|
| **DWH** | MS SQL Server 2008 | Snowflake/Azure Synapse (только агрегаты) |
| **Операционные БД** | Внутри DWH | PostgreSQL кластеры по доменам |
| **Data Lake** | Отсутствует | S3/Azure Data Lake Gen2 |
| **Event Streaming** | Apache Camel (ESB) | Apache Kafka |
| **BI** | Power BI с кастомизациями | Power BI + Self-Service Portal |
| **Интерфейс операторов** | PowerBuilder | Веб-приложение (React/Vue.js) |
| **ETL/ELT** | SQL в DWH | Apache Airflow + dbt |
| **Data Catalog** | Отсутствует | AWS Glue/Unity Catalog |
| **API Gateway** | Отсутствует | Kong/AWS API Gateway |
| **Финтех-сервисы** | Golang/Java | Golang/Java (без изменений) |
| **ИИ-сервисы** | Python | Python + MLflow + Feature Store |

### 1.5. Поддержка ключевых бизнес-сценариев

#### Сценарий 1: Быстрая подготовка отчётности
**Проблема**: формирование сложных отчётов занимает часы

**Решение в целевой архитектуре**:
- Domain Data Products предоставляют предагрегированные витрины данных
- Self-Service Portal использует оптимизированные аналитические хранилища (Snowflake)
- Materialized views и инкрементальные обновления (dbt)
- Кеширование часто используемых запросов
- **Результат**: время построения отчётов < 30 секунд

#### Сценарий 2: Независимое развитие финтех- и ИИ-направлений
**Проблема**: вся бизнес-логика в одном DWH, изменения в одном домене влияют на другие

**Решение в целевой архитектуре**:
- Каждый домен имеет собственные операционные БД и сервисы
- Domain Data Products изолированы друг от друга
- Взаимодействие только через стандартизированные API и события
- Независимые команды разработки и развертывания
- **Результат**: время выхода новых фич сокращается в 3-4 раза

#### Сценарий 3: Масштабирование для новых бизнесов
**Проблема**: добавление нового направления требует изменений в DWH и интеграционной шине

**Решение в целевой архитектуре**:
- Новый бизнес создает свой домен по стандартному шаблону
- Подключается к Data Lake и Event Streaming
- Создает свой Domain Data Product
- Автоматически появляется в Data Catalog и Self-Service Portal
- **Результат**: онбординг нового бизнеса < 2 недель (vs 2-3 месяца сейчас)

#### Сценарий 4: Сквозная аналитика по всем направлениям
**Проблема**: нужно видеть интегрированные метрики (например, lifetime value клиента)

**Решение в целевой архитектуре**:
- Data Warehouse агрегирует ключевые метрики из Domain Data Products
- Self-Service Portal предоставляет возможность строить отчеты по нескольким доменам
- Data Catalog позволяет находить нужные данные
- **Результат**: руководство получает сквозную аналитику в реальном времени

#### Сценарий 5: Соответствие регуляторным требованиям
**Проблема**: медицинские и финансовые данные требуют особой защиты

**Решение в целевой архитектуре**:
- Изоляция медицинских карт и исследований (не попадают в аналитику)
- Row-level security и column-level security в Data Products
- Полное логирование доступа к чувствительным данным
- Шифрование данных at rest и in transit
- **Результат**: соответствие требованиям GDPR, 152-ФЗ, требованиям ЦБ РФ

## 3. Проблемные места текущей архитектуры

### 3.1. Критические проблемы (Must Have)

| # | Проблема | Описание | Страдающие бизнес-сценарии | Влияние на бизнес |
|---|----------|----------|----------------------------|-------------------|
| **П1** | **Монолитный DWH как единая точка отказа** | Все данные и вся бизнес-логика в одном MS SQL Server 2008. Любой сбой парализует всю компанию | - Работа клиник<br>- Финтех-операции<br>- ИИ-диагностика<br>- Управленческая отчетность | **Критично**. Простой = потеря выручки во всех направлениях. Риск репутационных потерь. Невозможность оказания медицинских услуг |
| **П2** | **Устаревшая платформа (SQL Server 2008)** | Нет поддержки от Microsoft с 2019 года. Уязвимости безопасности. Не поддерживает современные объемы данных (сотни ТБ) | - Безопасность медицинских данных<br>- Соответствие регуляторным требованиям<br>- Масштабирование | **Критично**. Нарушение требований регуляторов (ЦБ, Минздрав). Риски утечек данных. Штрафы и потеря лицензий |
| **П3** | **Низкая производительность аналитики** | Отчеты строятся часами. Множество трансформаций в одной базе. Сотни ТБ данных | - Управленческие решения<br>- Операционная аналитика<br>- Финансовая отчетность | **Высокое**. Замедление принятия решений. Снижение конкурентоспособности. Низкая удовлетворенность пользователей |
| **П4** | **Невозможность независимого развития доменов** | Вся логика в DWH. Изменение одного направления влияет на другие. Длинные циклы согласования | - Вывод новых продуктов<br>- Адаптация к рынку<br>- Инновации | **Высокое**. Медленный time-to-market. Потеря конкурентных преимуществ. Сложность привлечения новых партнеров |

## 4. Приоритизация проблем

### 4.1. Метод MoSCoW

### 4.4. Рекомендуемая последовательность решения проблем

#### Фаза 1 (0-3 месяца): Критические проблемы
1. **П2**: Миграция с SQL Server 2008 → Cloud DWH (Snowflake/Synapse)
2. **П1**: Разделение DWH на домены + репликация для отказоустойчивости
3. **П3**: Создание Domain Data Products для ускорения аналитики

**Результат**: устранение критических рисков, соответствие требованиям регуляторов

#### Фаза 2 (3-6 месяцев): Архитектурная трансформация
4. **П4**: Выделение доменных сервисов и БД
5. **П6**: Разработка Self-Service Portal (MVP)
6. **П7**: Внедрение Data Catalog

**Результат**: независимое развитие доменов, начало работы с Self-Service Portal

#### Фаза 3 (6-9 месяцев): Оптимизация и расширение
7. **П5**: Стандартизация онбординга новых бизнесов
8. **П8**: Новый веб-интерфейс для операторов
9. **П9**: Полная миграция в облако

**Результат**: целевая архитектура реализована, готовность к масштабированию

#### Фаза 4 (9-12 месяцев): Доработка и улучшение
10. **П10**: Замена Apache Camel на Kafka
11. **П12**: Observability платформа

**Результат**: современная, масштабируемая, наблюдаемая архитектура
